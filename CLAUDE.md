# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Terraform provider (`greeddj/gitlabcommits`) built on the **Terraform Plugin Framework** (protocol 6, not SDKv2). It manages a bundle of files on one branch of one GitLab project and batches every change into **one commit per `terraform apply` per resource**. All Go code lives in the single package `internal/provider/`; `main.go` only serves it. GitLab access goes through `gitlab.com/gitlab-org/api/client-go/v3`. Supported GitLab is 19.x (what CI tests against); the technical floor of the API surface used is 14.10 (`execute_filemode`), and `allow_empty` (18.8) is not used: client-go still does not expose it at v3.12.0, and a zero-action apply makes no request at all.

## Commands

`just` is the entry point; every target is a thin wrapper over a Go/Terraform invocation (see `Justfile`). The analysis tools (`staticcheck`, `govulncheck`, `fieldalignment`, `tfplugindocs`, `copywrite`) are declared in the `tool` block of `go.mod` and run via `go tool ...`, so there is nothing to install. `golangci-lint` is the one external binary (CI pins v2.13.2; `.golangci.yml` enables an explicit linter list with `default: none`, so a new golangci-lint release cannot quietly add linters).

```bash
just ci              # the exact gate CI runs: check + lint + test + check-tf-fmt + check-examples + docs-check + headers-check + check-deps
just check           # go vet + staticcheck + govulncheck + fieldalignment
just lint            # golangci-lint run ./...
just test            # go test -race ./...   (CI adds a coverage profile)
just build           # check + lint + test, then a CGO_ENABLED=0 static binary in ./dist (version from `git describe --tags`, falls back to 0.0.0-dev)
just docs            # go generate ./... -> tfplugindocs regenerates docs/
just docs-check      # regenerate and fail if docs/ is dirty
just fix             # go fix + fieldalignment -fix
just headers         # apply copywrite license headers (headers-check verifies)
just tf-fmt          # terraform fmt -recursive examples/ (check-tf-fmt verifies)
just check-examples  # scripts/validate-examples.sh: builds the provider, then terraform validate over examples/{complete,for_each,provider} via dev_overrides
just deps            # go mod tidy (check-deps runs go mod tidy -diff)
```

Single test (everything is in one package):

```bash
go test ./internal/provider -run 'TestDiffActions' -v
go test -race ./internal/provider -run 'TestRead_' -v   # use -race for anything touching the goroutine fan-outs
```

### Acceptance tests

`TestAcc*` in `files_resource_acceptance_test.go` run against a real GitLab project. They `t.Skip` without `TF_ACC` and `t.Fatal` when `TF_ACC` is set but the token or project is missing, so plain `just test` stays green.

```bash
export TF_ACC=1
export GITLAB_TOKEN='...'                  # api scope (see README Authentication)
export GITLAB_TEST_PROJECT_ID='you/sandbox' # plain path (not URL-encoded) or numeric ID
export GITLAB_TEST_BRANCH='tf-acc-test'    # optional; this is the default; must pre-exist unless GITLAB_TEST_BRANCH_FROM is set
export GITLAB_TEST_BRANCH_FROM='main'      # optional; tests add create_branch_from and delete the branch afterwards
export GITLAB_BASE_URL='https://gitlab.example.com'  # optional, self-hosted
go test -v -timeout=20m -run '^TestAcc' ./internal/...
```

Every acceptance file path lives under `tf-acc-test/` (`accTestPathPrefix`) so a stuck run is easy to clean up. In CI (`.github/workflows/acceptance.yml`) they run on manual dispatch, a nightly cron, and pushes to `main` touching `internal/**`, on a unique per-attempt branch `tf-acc-test-<run_id>-<run_attempt>` created from `main`; an `if: always()` step deletes it over the API even when the job times out or is cancelled.

## Architecture

### Files

- `provider.go` - provider schema and `Configure`; builds one `*gitlab.Client`, hands it to data sources through `DataSourceData`, and to resources through `ResourceData` as `*resourceDeps` (client + that configuration's `branchLocks`, which also holds the path claims + whether the commit request may be retried).
- `files_resource.go` - the only resource, `gitlabcommits_files`: schema, `ModifyPlan`, CRUD, import, `diffActions`, `stampBlobs`, `apiErrorDiag`, `decodeRemoteContent`.
- `file_datasource.go`, `branch_head_datasource.go` - `gitlabcommits_file` (one file at a ref) and `gitlabcommits_branch_head` (head SHA + protected flag).
- `schema_validators.go` - validators the framework lacks: regex, non-empty, sibling mutual exclusion, exactly-one-of file content (null entries included), map-key repository path check, git ref name.

### Provider client (`provider.go`)

The token comes from the `token` attribute or `GITLAB_TOKEN`; the base URL from `base_url` or `GITLAB_BASE_URL`. Retries (`max_retries` default 5, `retry_wait_min_ms` / `retry_wait_max_ms` 1000 / 30000) are configured at client construction; an unknown value at configure time is an error, never a silent default. client-go's default retry check replays any request on 5xx regardless of method, so `POST /repository/commits` carries its own per-request policy (`commitRetryPolicy`, attached by `commitRequestOptions`): retry only on 429 and on transport failures `isPreWireTransportError` classes as happening before the request is sent (any name lookup, a dial, a TLS handshake timeout, and the same inside the `OpError{Op: "proxyconnect"}` net/http wraps every proxy connection failure in, so a permanent proxy error such as a certificate is not retried), except an NXDOMAIN, which will not resolve on a retry either; never on 5xx or a broken connection, because a replay after GitLab already landed the commit would be a second commit for one apply. `max_retries = 0` disables that policy too (`resourceDeps.retryCommits`), since a per-request check would otherwise bypass `WithoutRetries`. client-go v3 offers `WithOnlyIdempotentRetries()`, which scopes 5xx replays to idempotent methods and looks like it would retire all of that; it is deliberately not used, because it still routes a POST's transport errors through the generic check, where a post-wire read timeout satisfies `net.OpError.Temporary()` and would be replayed into a second commit. The retry wait bounds only shape the 429 backoff; client-go uses a fixed 700-900 ms schedule for 5xx. Configure rejects a token with surrounding whitespace or control characters (a trailing newline from a file is the usual case) and a `base_url` without an http(s) scheme and host, because client-go only logs its own URL validation failure. The HTTP client is cleanhttp's pooled transport with a `ResponseHeaderTimeout` of five minutes (`responseHeaderTimeout`; uploads are not bounded) and `crossHostRedirectGuard` as `CheckRedirect`: net/http does not strip the `Private-Token` header on cross-host redirects, so off-host redirects and https->http downgrades are refused by returning `http.ErrUseLastResponse`, which hands the 3xx to client-go as a plain non-2xx (not retried; an error from `CheckRedirect` would be replayed as a transport failure) and `apiErrorDiag` reports it with the `Location`.

### Per-branch commit serialisation

Terraform applies resource instances concurrently (`-parallelism`, default 10), and the documented `for_each` layout puts many resources on one branch. Two `CreateCommit` calls racing on the same branch tip make Gitaly reject the loser with HTTP 400 "reference update: reference does not point to expected object". `branchLocks` (one per provider configuration, created in `Configure` and shared through `resourceDeps`; Terraform runs each provider block in its own process, so two aliased provider blocks are not serialised against each other) serialises commits per `(project_id, branch)`: Create runs the branch check, preflight and adopt probes unlocked (they only read; the probes come after the claim pass below), then takes the lock, re-checks the branch under it (two instances materialising the same branch must see each other's work; one that finds the branch created meanwhile probes it again under the lock, since the branch now holds the other instance's commit) and holds it through `CreateCommit`, releasing before `stampBlobs`, which probes the immutable commit; Update and Delete hold it only around `CreateCommit`, through `commitLocked`, the one place that runs under the lock right before their commit (a wait cancelled by ctx comes back as `errLockWait`, which `commitErrorDiag` reports as such: nothing was sent). `acquire` is channel-based so it honours ctx cancellation, and the release it returns is idempotent (`sync.OnceFunc`), so Create defers it for its early returns and also calls it right after the commit. The key is the verbatim `project_id` string, so resources sharing a branch must spell it the same way (numeric ID and path are different keys), and only the target branch is locked, not the `create_branch_from` source, which is why Create pins the source to a commit before it probes (see Create below). The lock changes ordering, never the number of commits. Writers outside the process (another pipeline, a manual push, an aliased provider block) are not covered by design; `apiErrorDiag` recognises the Gitaly text and says so.

`branchLocks` also holds the path claims, in memory for the life of the process (nothing goes to state, disk or GitLab). One apply can hand a path from one resource to another on the same branch: a file moved between two `files` maps, an address renamed without a `moved` block, a replacement under `create_before_destroy` (Create of the new object strictly before Delete of the deposed one). Terraform does not order the giver's delete before the receiver's adoption, and an adoption of identical content makes no commit, so the delete would land on a still-valid `last_commit_id` and leave the receiver's state claiming a file that is gone. A claim is `(project_id as written, branch, path)`: Create claims every plan path and Update the paths it adds (`addedPaths`), and `claimPaths` registers them and then passes through the branch lock once (acquire, release) before the adopt probes, so a delete commit already in flight lands before the probe. Under the lock, right before `CreateCommit`, `commitLocked` runs `withoutClaimedDeletes`, which drops the delete of every claimed path with a warning naming it; when nothing is left it sends nothing and returns an empty `sent`, which Update treats like its zero-action path and Delete as done. The creates left are checked against the claims as well (`createsOverClaims`, see Update). Either the delete lands first and the receiver re-creates the file, or the delete is dropped; the commit count per resource never grows. A claim under another spelling of the same branch and path is resolved to numeric IDs, only when such an overlap exists: an all-digit spelling is its own ID (`allDigitProjectID`; GitLab resolves an all-digit `project_id` by ID, and a project path always holds a slash), a path spelling takes one `GetProject`, cached in `branchLocks.projectIDs`. The claim key carries no project, so different projects sharing a branch name and a path also meet there; with numeric IDs that costs nothing. A failed lookup fails the operation with a diagnostic naming both spellings and the path, never a silent delete or skip, and that diagnostic says not to simply apply again: a re-run is a new process without the claim, so the retried delete would land. Claims are never released (a failed Create keeps its claim, so the file stays), and a resource never blocks its own deletes, since the paths it claims are never among those it deletes in the same operation. Delete's fallback after a rejected commit probes and retries only what `commitLocked` sent, and its `nothingDeleted` warning sets the kept files apart. The in-flight ordering relies on the branch lock, so it still needs the same spelling; other runs (a re-run of a failed apply included) and aliased provider blocks are not covered.

### The one-resource model

`gitlabcommits_files` owns `map(path -> file)` on one branch of one project. `project_id` and `branch` are `RequiresReplace` (deliberately kept even though an unknown plan value, or a respelled `project_id`, forces a replacement that may end up targeting the same branch: skipping replacement on unknown would break the plan contract when the value does change; the README documents `moved` / `removed` blocks instead); the ID is `<project_id>::<branch>`. Multi-branch or multi-project setups are expressed with `for_each` over resources, never by widening a single resource. An apply that changes anything produces exactly one commit per resource; an apply that changes nothing produces none; and state never claims a file GitLab does not have. This is the load-bearing invariant of the whole provider. A path may move between resources on one branch within one apply; the path claims (above) keep that invariant across them.

### CRUD as action-diffing

- **Create** checks the branch (`branchExists`). If it is missing, `missingBranchPreflight` resolves the commit the branch will start from (`base`): a 40/64-hex `create_branch_from` as it is, lowercased (Gitaly takes only lowercase hex as `start_sha`), a branch name through `GetBranch` to its head (a 404 there says tags are not supported; a nil `Commit` or empty id is an error). Resolving once keeps the probes and the new branch on one tree even when another resource in the same apply moves the source branch meanwhile. A repository with no commits (`empty_repo`) has no ref to start from: without `create_branch_from` the base stays `""`, nothing is probed (nothing can exist), and the commit carries `branch` alone, which GitLab turns into the root commit together with the branch (the API defaults `start_branch` to `branch`, `Commits::CreateService` skips its branch checks for an empty repository, and Gitaly's `resolveParentCommit` returns no parent when the repository has no branches); with `create_branch_from` set it is an error saying to remove it. The paths are then probed at the branch, or at `base` when the branch does not exist yet, by `probeAdded` (see Update for what it checks), and `adoptAwareActions` rewrites a `create` for an existing path into an `update`, plus a companion `chmod` when the exec bit differs (the commits API honours `execute_filemode` only on create and chmod; GitLab's docs claim chmod only, create is verified by `TestAccFiles_chmodCycle`). The adopt probe also fetches the content (one `GetFile` per existing path), and a path whose bytes and mode already match the plan yields no action; when nothing is left to commit, Create makes no commit and writes `commit_sha` null. A missing branch is materialised by `start_sha = base` on the commit itself, never `start_branch`: GitLab creates the branch and the commit in one operation, so a server-side rejection (push rule, pre-receive hook) leaves no orphaned empty branch and CI sees one push event; the diagnostic for that failure names the branch, the `create_branch_from` ref and `base`. That commit carries no `last_commit_id`: with `start_sha` and no `start_branch`, GitLab's `file_has_changed?` compares the token with the path's last commit on the default branch, not on `base`, and `base` is immutable anyway, so a token would only fail on a path the default branch changed since. The one exception is the zero-action case, where there is no commit to attach `start_sha` to and the branch is created with a bare `CreateBranch` at `base` (`createBranch`); client-go replays that POST after a 5xx, so when it fails Create checks the branch again under the lock and takes "it exists now" as success with a `tflog` warning. The branch check and preflight run first; then `claimPaths` claims every plan path and passes through the branch lock, and only then the probes run (all unlocked, they only read); the lock is taken again for the re-check of the branch and the commit, and a branch found created meanwhile is probed again under it, the tokens kept since the commit then targets that branch; `createsOverClaims` runs under it before the commit.
- **Read** is a no-op when `detect_drift = false`. Otherwise it fans out `GetFileMetaData` (HEAD-style, no body) at `refreshParallelism` (16) through an `errgroup`, compares `blob_id` and the exec bit with state, and pulls full content with `GetFile` only for files that actually drifted. A metadata response whose ids `checkFileIDs` rejects (a missing `blob_id` or `last_commit_id`, or one longer than `maxBlobIDLen`) is an error: a missing blob id would compare as "unchanged" forever. The same rejection on the `GetFile` body only warns, leaving `blob_id` null and taking `last_commit_id` from the metadata response. A 404 drops the file from state, but only once `branchExists` has answered: a Gitaly failure reaches the Files API as a 404 while the branch lookup reports it as an error, which fails the refresh with state unchanged (see Delete). If *every* file 404s and the branch is gone too, or there are no files yet (right after import) and the branch is gone, it removes the whole resource so the next apply can recreate it; a branch that 404s while another file still answered only drops the 404'd files. Goroutines write only to their own slot of a pre-sized `[]fileRefreshResult`; a serial second pass mutates `state.Files` in path order. Whichever of `content` / `content_base64` the user chose is preserved on drift (`setRemoteContent`), except for bytes `content` cannot hold (`textContentMisfit`: invalid UTF-8, which cty would silently turn into U+FFFD): those are recorded in `content_base64` with `content` null and a warning naming the path. Read never sees the configuration, so an error there would block every refresh whatever the file is switched to; with the fallback the next plan shows the configured text replacing the bytes (one update, carrying the token that refresh read) or, once the file is switched to `content_base64` of the new bytes, nothing to do. Another condition that keeps bytes out of `content` belongs in `textContentMisfit`.
- **Update** first claims the paths it adds (`claimPaths`, see the path claims above), then calls `diffActions`: path gone from the plan -> `delete` (emitted first, so a path can turn from a file into a directory, or a directory of managed files into a file, within one commit), new path -> create or adopt-update, content changed (`contentChanged`: cheap string compare first, bytewise fallback only for differing base64 or a form switch) -> `update`, exec bit flipped -> `chmod`. The adopt probe also fetches the remote content: a path whose bytes already equal the plan yields no action (only a `chmod` if the exec bit differs), so the import round-trip and a re-pointed resource make no commit. Zero actions means no commit; computed fields are carried over from state, or from the probe for adopted-identical paths (`carryOver`). The new paths go through `probeAdded`, shared with Create: with adoption on, `probeFile` per path (metadata, ids checked by `checkFileIDs`, then content), and for every path that will be created (absent, or adoption off) `directoryEntry`, a one-entry `ListTree` at the path. Gitaly applies a create with `WithOverwriteDirectory`, so a create over a directory silently replaces it with everything in it; a directory there fails the file, unless the commit deletes paths inside it, in which case `fileKeptUnder` lists it recursively (offset pages) and allows the create only when the commit deletes every file in it. The tree API answers 404 for a path that is missing or holds a file, and also when Gitaly fails to resolve the ref (the endpoint answers `not_found!("Tree")` when `project.commit(ref)` is nil, which a Gitaly error makes it), so a directory check that answered 404 is trusted only once one `branchExists` after the fan-out has answered (`treeGitaly404Note`); that lookup reports a Gitaly failure as an error whether or not the branch exists, so it vouches for a listing at `base` too. The directory check runs unlocked, so a directory another resource in the same run fills after it is caught by the claims instead: under the lock, right before the commit, `createsOverClaims` (called by `withoutClaimedDeletes` for Update, directly by Create) fails a create of `p` when a path inside `p/` is claimed on the branch by the same project under any spelling (`claimedInside`, resolved like a delete's claim). That also covers a delete `withoutClaimedDeletes` drops inside a directory the commit turns into a file. Any probe error (a failed request after a successful HEAD included) fails the file through `apiErrorDiag` before the lock, never a fallback to create or update: a create would fail on "already exists" and hide the cause, an update could commit content that already matches. Every per-file failure is an attribute error on `files[path]`, and Create and Update report one cause identically (`fileActionDiags` for an action that cannot be built). A locked adoption whose probe carries no `last_commit_id` is an error, never a silently unlocked write. A delete or chmod that goes out without a `last_commit_id` (`optimistic_lock = false`, or no token in state) is probed first by `probeUnguarded`, because GitLab's only guard is that token: without it Gitaly applies the action to whatever tree entry sits at the path, so a delete removes a directory that replaced the file and a chmod gives a tree a file mode. A delete whose path no longer holds a file is dropped, a chmod of one fails naming the path; paths the adopt probe just resolved are not probed again, and the default (lock on, every token present) makes no extra request. A delete of a path another resource claimed in this process is dropped under the lock by `commitLocked`; if that leaves nothing, Update makes no commit and keeps `commit_sha`. A refresh is handed the prior state and no configuration, so it reads the *stored* `detect_drift`, and a failed apply keeps that value: a new value only affects refreshes once an apply has recorded it. So with `detect_drift = false` in the prior state (whatever the plan says) a file deleted out of band is still in state, and Update passes `unrefreshed` to `probeUnguarded`, which then probes every delete, locked ones included, in the same one fan-out as the token-less deletes and chmods, and drops the ones whose path no longer holds a file; the token of a delete that is kept stays, so a file changed out of band still fails the commit. Without that, the locked delete of a missing file would fail with GitLab's 400 ("has changed since") on every apply, the one re-enabling `detect_drift` included. Updates and chmods are not probed or re-tokened: a stale token there is a real conflict, and refreshing inside Update would commit reverts the plan never showed. The recovery for those is recording `detect_drift = true` with `files` as last applied (no commit, `recordDetectDrift`), then putting the change back and planning (`replanWithChange`: with `files` still as last applied that plan would revert whatever landed, a commit whose apply failed included); `unrefreshedNote` and the chmod-of-a-missing-file error both give it.
- **Delete** with `delete_on_destroy` (default true) builds a delete for every path in state and sends it first, without probing, for every path whose action carries a `last_commit_id`: GitLab checks the token itself and rejects the whole commit (HTTP 400, nothing lands) when a file was changed, removed or replaced out of band. Token-less deletes are probed first (`probeUnguarded`). On a 400, or a 404 (the project gone or invisible to the token; GitLab answers both before it writes anything), `absentPaths` probes every remaining path; if all are present the original error is reported, otherwise the commit is retried exactly once without the absent paths, and a second rejection fails with its own diagnostic. So at most one commit ever lands. Both commits go through `commitLocked`, so a path another resource claimed in this process is left in place with a warning, and when every delete is dropped nothing is sent. `absentPaths` trusts a 404 only after `branchExists` answers (a probe *error*, anything but a 404, fails at once): GitLab answers the Files API with 404 when Gitaly times out resolving the ref (up to at least 19.4 also when Gitaly is down; an upstream change after 19.4 answers that case with 503, but a timeout still comes back as 404), while `find_branch` reports the same failure as an error, so that error fails the destroy. This narrows the window rather than closing it: a timeout that clears before the branch lookup still reads as absent. A branch lookup that 404s is accepted (the files cannot outlive their branch) and only changes the warning. When nothing is left to delete, destroy succeeds with a warning (`nothingDeleted`), whose text says the files may still exist when the branch is not visible either (deleted, project removed, or the token lost access). Any other failure of the first commit (5xx, 403, a cancelled lock wait) is reported without probing: a 5xx may have landed. Delete reads `optimistic_lock` from state and passes no `unrefreshed` flag: a locked delete of a missing file is already handled by the fallback on the 400.
- **Import** takes `<project_id>::<branch>` and checks that the branch exists (a typo would otherwise only surface as an empty, unfixable resource); the files map starts empty and the next apply converges through adoption, without a commit when the repository already matches.
- **Plan** (`ModifyPlan`): once the planned object differs from prior state at all, the framework's `MarkComputedNilsAsUnknown` plans every Computed attribute without a config value or default unknown, so without `ModifyPlan` a one-file edit would list every file's `blob_id` / `last_commit_id` and `commit_sha` as known after apply, and so would a `commit_message` edit that commits nothing. `ModifyPlan` puts back the prior values an apply keeps: for a path in both plan and state whose `content`, `content_base64` and `execute_filemode` are `Equal` to state (`fileKept`; null-ness included, and prior state holds no unknowns, so an unknown never passes) the prior `blob_id` / `last_commit_id`, since `diffActions` emits no action for it and `carryOver` copies exactly those; and `commit_sha` when the key sets are equal and every file is kept, since Update then takes the zero-action branch. Nothing else in the plan can make Update commit (`commit_message`, author and the flags only shape a commit or the adds and deletes, and there are none). The test is deliberately stricter than `contentChanged`: a form switch with identical bytes stays unknown, which is always safe (unknown may become anything). A later drop of a delete (a claim, a token-less probe) only turns a planned-unknown `commit_sha` into the old one. Create and destroy (null state or plan), an unknown or null `files` map, an unknown element and a changed or unknown `project_id` / `branch` (a replacement, which Terraform plans again with a null prior) keep the framework's unknowns; the files map is rebuilt and set once, not per attribute, because `SetAttribute` transforms the whole value. `UseStateForUnknown` on `blob_id` / `last_commit_id` would be wrong: the framework resolves prior state per map key, so a changed file would be planned with its stale id and the apply would fail as an inconsistent result.

### Optimistic locking and blob stamping

With `optimistic_lock` (default true) every update / delete / chmod action carries the file's `last_commit_id` from state (or from the probe, for adopt-updates), and GitLab rejects it with HTTP 400 if the file changed after the refresh or apply that recorded that token. Read refreshes the token on purpose (a drifted blob, or a last commit that moved), so with `detect_drift = true` an out-of-band edit made before the plan's refresh is not rejected: the plan shows its revert and the apply overwrites it. The lock guards the window from that refresh to the commit (or from `plan -out` to applying the saved plan), and for an adopt-update, whose token the apply's own probe reads, only the window from that probe to the commit; the `optimistic_lock` and `last_commit_id` descriptions, README and the conflict diagnostic say so rather than promising more. `apiErrorDiag` recognises that 400/409 body through `isLockConflict` (`last_commit_id` / `last commit` / `has changed since`) and turns it into a "Concurrent modification detected" diagnostic, and the Gitaly ref-race bodies (`expected object`, the tip moved, or `already locked`, another writer held the ref lock past git's timeout; never the bare `reference update:` prefix, which also carries causes a re-run cannot fix) into "Branch changed while the commit was being created" (a writer outside this terraform run); it also maps 401 / 403 / 404 / 413 / 429 / 3xx / 5xx to actionable text and truncates bodies to `maxDiagBodyChars`. The caller's action appears exactly once: in the default summary, or at the head of the detail when a recognised case replaces the summary. Commit requests go through `commitErrorDiag` instead, which adds that the commit may or may not have landed for a 5xx and for a transport failure `isPreWireTransportError` does not clear (`commitMayHaveLanded`), since a commit request is never replayed once it may have reached GitLab; a read's 5xx says nothing about commits. `absentPaths` reports failed probes as one diagnostic for the first path plus the others by name (`alsoFailed`), since a revoked token fails every probe alike. An Update commit rejected with a 400 is followed by a `branchExists`: a branch gone since the plan (a merge request that deleted its source branch) reads as "Branch no longer exists" with the recovery for the `detect_drift` value in state (`branchGoneDetail`), because GitLab's own text ("You can only create or edit files when you are on a branch") names no branch; Create gets the same text for a missing start branch, so the check sits at the Update call site, not in `apiErrorDiag`. `apiErrorDiag` has no model, so Update and Delete append `unrefreshedNote` to a commit error themselves: when the *prior state* records `detect_drift = false` (the value the next refresh reads, not the plan's), a lock conflict (`isLockConflict`) or a commit that may have landed (`commitMayHaveLanded`) gets the recovery that works, since the refresh or plan the base text suggests changes nothing then; Delete gets its own variant (a 5xx destroy is safe to re-run). For an Update lock conflict, `optimistic_lock = false` is offered only as a shortcut for overwriting a file that still exists: Update probes no updates, so a token-less update of a file deleted out of band gets GitLab's "doesn't exist" 400, and after a 5xx whose commit landed it would commit the same change again. Destroy can offer it as a full route, since token-less deletes are probed. Both the lock-conflict and the ref-race text also name a tag with the branch's name (`tagShadowHint`): GitLab resolves the bare name to the tag first, and its commits API computes the expected branch tip (`Repository#commit_files`) and walks `last_commit_id` (`Files::BaseService#file_has_changed?`) through the bare name, so with such a tag every commit fails the same way on every run. The provider's probes send the bare name as `ref` as well, so they read the tag's tree; a branch that shares its name with a tag is documented as unsupported (Limits) rather than handled. Probe refs are deliberately not qualified as `refs/heads/<branch>`: it would not fix the commit-side checks, and it is not acceptance-tested, while a qualified ref the Files API did not resolve would make Read drop every file. `gitlab.ErrNotFound` is itself an `*ErrorResponse` carrying `StatusCode: 404` and a nil `Response`, and `CheckResponse` answers every 404 with that one shared value before it reads the body, so a 404 never carries one. `(*ErrorResponse).Is` matches on the status code alone, so `errors.Is(err, gitlab.ErrNotFound)` asks whether some `*ErrorResponse` in the chain is a 404, which is what every 404 check in the provider wants. It also means `errors.AsType[*gitlab.ErrorResponse]` now matches a 404, though the status switch still skips the sentinel on its nil `Response` guard; `apiErrorDiag`'s `errors.Is` branch is what turns a 404 into its own diagnostic instead of the bare error string, and it runs first so that a 404 arriving with a `Response` attached does not fall into the switch's default. `TestApiErrorDiag`'s `404-with-response` case pins both.

After every successful commit `stampBlobs` refreshes `blob_id` and `last_commit_id` for the paths the commit touched (`touchedPaths`; the set is required, and nil stamps nothing) through a parallel metadata fan-out probing at `Ref = commitSHA` - the commit just created, **not** branch HEAD - so a racing writer's values can never be stamped next to our content. Untouched paths are not probed; `carryOver` keeps their state values, so a probe hiccup can never stamp the new commit's SHA next to a file it never modified. A probe failure, or ids `checkFileIDs` rejects (missing, as in a header-less 2xx, or longer than `maxBlobIDLen`, 256, treated as hostile), leaves `blob_id` null with a warning; the next Read repopulates it. `checkFileIDs` is the one bound on server ids: Read, `stampBlobs` and `probeFile` all use it, so no path stores an unusable id or sends one back as a lock token. A nil commit or an empty commit id from a 2xx is an error without state on Create on purpose: returning state would make Terraform taint and replace the resource (a delete commit), while a re-run converges through adoption.

### Validators and schema conventions

Custom validators live in `schema_validators.go`; defaults use the framework's `booldefault.StaticBool` inline in the schema. `files` carries `mapNonEmpty()` on purpose: `files = {}` would mean "delete everything" on update, which is what `terraform destroy` is for. `mapKeysValidRepoPath` uses explicit segment logic instead of a character regex so legal git names like `..config` stay usable; only `.` / `..` segments, empty segments, NUL bytes and leading whitespace are rejected, the rest is GitLab's to validate. The same rules back `stringValidRepoPath` (the file data source's `file_path`); `stringBranchName` is the shared git ref-name check for `branch` and `create_branch_from` on the resource and `branch` on both data sources (`validateRefName`: git check-ref-format's rules plus the leading dash `--branch` rejects, so `+`, `@`, `#`, `,` and non-ASCII names pass and `..`, `@{`, `.lock` segments and the like fail; `HEAD` and a `refs/heads/` prefix are left to GitLab; `:` has to stay rejected, since the resource and import IDs join project_id and branch with `::`; hex commit SHAs pass); `stringIsBase64` rejects a non-decodable `content_base64` at plan time. `content` / `content_base64` are exactly-one-of via `stringConflictsWithSibling` plus `objectFileContentRequired`, and neither is `Sensitive` by design (see SECURITY.md). `objectFileContentRequired` also rejects a null `files` entry (`"p" = null`, typical of a conditional inside `merge()`): the framework runs a map-nested object validator for null elements too, and without the check the entry passed validate and plan and only failed at apply with a "Value Conversion Error" worded as a provider bug.

### Hardening guards worth keeping

Nil guards exist for a 2xx JSON-null body from `CreateCommit` (nil `*Commit`), `GetFile` (nil `*File`), `GetBranch` (nil `Commit`, in the branch-head data source and when resolving `create_branch_from`) and `ListTree` (a nil entry or one without a path); `decodeRemoteContent` fails loudly on an unknown encoding. `hardening_test.go` and `create_test.go` pin these.

## Testing patterns

- Unit tests fake GitLab with `httptest.NewServer` and `gitlab.NewClient("tok", gitlab.WithBaseURL(srv.URL+"/"), gitlab.WithoutRetries())` (retries off so a faked 5xx does not stall behind the backoff schedule). CRUD is driven directly: build `tfsdk.State` / `tfsdk.Plan` from the resource schema and call `Read` / `Create` / `Update` / `Delete`. Reuse `runRead`, `readState`, `newReadClient`, `newTestResource` (`read_test.go`) and `runCreate`, `runUpdate`, `runDelete` (`crud_test.go`) rather than adding new harnesses. `newRetryingResource` builds the `max_retries > 0` wiring (retrying client with millisecond backoff plus `commitRetryPolicy`) for retry tests; the `run*On` variants drive a pre-built `filesResource`; `createRequest` / `updateRequest` / `deleteRequest` build the request on the test goroutine so concurrency tests can call `Create` / `Update` / `Delete` from workers without `t.Fatalf` leaving the test goroutine, and `inFlight` measures how many commit requests overlapped; `createOp` / `updateOp` / `deleteOp` (`claims_test.go`) wrap the same builders into an operation to run on any goroutine and read its diagnostics and state afterwards. `repoFake` is a small stateful GitLab (path -> last commit id, which also answers tree listings; every file's content is "x" unless `content` overrides it per path) that rejects commits the way GitLab does (create of an existing path, a missing path or a stale `last_commit_id` on update / delete / chmod, any commit on a missing branch) and records every commit (as `describeActions` renders it) and probe, so the Delete and probe tests pin exact commit bodies and request counts. Every `project_id` spelling reaches the same files; `projects` answers `GetProject` per spelling (a lookup is an unexpected call while it is nil), and `beforeCommit` runs as a commit arrives, outside the fake's lock, so a test can hold a commit in flight. `handler` serves the fake for a test that wraps it, for example to run another operation right after a request is answered (the answer reaches the client only once the wrapper returns). Every create makes a tree request (the directory check), and a 404 there one branch lookup to confirm it; a hand-written handler answers the tree request with `isTreeRequest` / `noDirectory`, and a missing target branch with `branchJSON` for `create_branch_from = "main"` at `sourceHead` plus `projectJSON`.
- The CRUD harness mirrors fwserver, so a test cannot pass on a value the framework would never hand the resource. `runRead` starts the response as a copy of the current state, `updateRequest` starts it as the prior state and `createRequest` as a typed null state. `plannedModel` (applied by both request builders, with the prior state on Update and nil on Create) marks `commit_sha` and every file's `blob_id` / `last_commit_id` unknown in the plan, and `id` too on Create; on Update `id` keeps its prior value, as `UseStateForUnknown` plans it, and it restates what `ModifyPlan` keeps (a kept file's ids, and `commit_sha` when every file is kept), independently of the production code. A test that needs `carryOver` or the zero-action branch to fill a file's ids from state therefore switches that file between `content` and `content_base64` of the same bytes: that needs no action, but the plan leaves its ids (and `commit_sha`) unknown, as `TestUpdate_StampsOnlyTouchedPaths` and `TestUpdate_NoOpPreservesUnknownComputedFields` do. `TestPlannedModel_MatchesFramework` compares that plan with what `PlanResourceChange` produces for a Create and several in-place Updates, so a Computed attribute added to the schema, or a change to what `ModifyPlan` keeps, must be mirrored in `plannedModel` too. The files map is copied first, so a test may pass one model as both plan and state. `runRead` and `checkCreateResult` / `checkUpdateResult` (called by `runCreateOn` / `runUpdateOn`, and from the workers of the concurrency tests, since they only call `t.Error`) require a successful call to return a fully known state, a failed Create to return no state, and a failed Update to leave the prior state exactly as it was; a successful Update must also keep every value the plan knew (`checkKeepsPlan`, Terraform's "inconsistent result after apply" check). Error-path tests therefore pin the no-state-on-error contract, and Update tests the plan contract, without asserting it themselves.
- Schema wiring (validators, `RequiresReplace`, `ModifyPlan`) is tested at the protocol level in `files_resource_protocol_test.go`: `protocolServer` serves the provider through `providerserver`, and `filesValue` / `configOf` encode a model as a protocol value or as configuration for `ValidateResourceConfig` and `PlanResourceChange`; `replacedAt` makes one value null or unknown, which a model cannot encode, and `valueAt` reads one back. `TestUpdate_AppliedStateKeepsThePlan` hands Update the framework's own plan. No Terraform binary or network is involved, so these run in `just test`.
- `files_resource_terraform_test.go` runs Terraform itself (`resource.UnitTest`, no `TF_ACC`) against `repoFake` served by `httptest`, with `base_url` pointing at it, and checks the plans with `plancheck`; Terraform's own plan and apply consistency checks run too. It needs a terraform CLI on PATH (CI's `setup-terraform` provides one) or `TF_ACC_TERRAFORM_PATH`, and skips without one rather than letting terraform-plugin-testing download a release.
- Acceptance tests use `terraform-plugin-testing` (`resource.Test` with `testAccProtoV6ProviderFactories`), render HCL with `accConfig`, and assert against the API with `accCheckFileExists` / `accCheckFileGone` / `accCheckFileExec`.

## Docs, examples, and release

- `docs/` is generated by `tfplugindocs` (`//go:generate` in `main.go`) from schema descriptions plus `examples/provider/provider.tf`, `examples/resources/gitlabcommits_files/{resource.tf,import.sh}` and `examples/data-sources/<name>/data-source.tf`. The only template is `templates/index.md.tmpl`, which adds the Authentication and Limits sections to the provider page (the `token` description points at them); resource and data-source pages use tfplugindocs' defaults. Any schema, description or template change must be followed by `just docs` with the result committed; CI fails on drift.
- Go version bump checklist: `go.mod` (`go get go@1.NN.P`, patch included), `go get -u ./...` plus `go get -u tool` (the `tool` block and test-only imports are not covered by `./...`), `.golangci.yml` `run.go`, the golangci-lint `with: version:` pin in `ci.yml` (a prebuilt binary older than the Go release cannot type-check the module; nothing bumps `with:` inputs automatically), and the version text in README.md and CLAUDE.md. A patch bump moves `go.mod`, the dependencies, and README's `Go >=` floor, which mirrors the `go` directive; `.golangci.yml`'s `go:` key and README's `(Go 1.27 default)` note name the language minor and stay put, and the golangci-lint pin moves on golangci-lint's own release schedule rather than with Go.
- `google.golang.org/grpc` is held at v1.83.2 by an `exclude` of v1.84.0 at the foot of `go.mod`. The advisory behind GO-2026-6443 / GHSA-2v4p-qf9q-27wj carries a third range, `>= 1.84.0-dev, < 1.85.0-dev.0.20260825072537-93e31b48545e`, that tracks grpc's master branch rather than a release line, and semver places the released v1.84.0 inside it. So `govulncheck` fails a version that already carries the fix: the `no host or :authority header present` guard from grpc-go PR #9365 is absent in v1.83.1 and present verbatim in v1.83.2 and v1.84.0 alike, and the panic it describes needs xDS routing, which a provider served by `providerserver.Serve` never reaches. `govulncheck` has no per-ID suppression, so the version has to be kept out of the graph. It is an `exclude` rather than a `require` pin because `go get -u ./...`, step two of the checklist above, silently raises a `require` pin and honours an `exclude`. The directive names one version, so the first `go get -u ./...` after grpc ships v1.85.0 moves past it unaided; delete the directive then.
- `examples/complete`, `examples/for_each` and `examples/provider` are full modules that CI runs `terraform validate` on against the locally built provider; keep them valid. New API surface needs an example there so the docs pick it up.
- License headers are enforced by `copywrite` (`.copywrite.hcl`; `examples/`, `.github/`, `docs/` are exempt).
- A `v*` tag triggers `.github/workflows/release.yml`, whose first job calls `ci.yml` through `workflow_call` (the gate is defined once; the tag run passes `CODECOV_TOKEN` explicitly and no other secret), then goreleaser (GPG-signed, `main.version` set via ldflags). The changelog is built from conventional commit titles (`feat:`, `fix:`, `docs:`; `chore:` and `test:` are excluded); there is no CHANGELOG file. Dependabot PRs use `fix(deps)` / `fix(ci)` with no `include: scope`: a second `(deps)` scope would miss the changelog's dependency group. The goreleaser CLI is pinned to an exact version rather than to `~> v2`, so the binary that built a tag is the one a commit names; dependabot moves the action's SHA but never a `with:` input, so that line is bumped by hand, as the golangci-lint pin is.
- `go.mod` is the single source of truth for the Go version (1.27.1); `.golangci.yml` mirrors its minor, which is all golangci-lint's `go:` target takes.

## Code conventions

- Default to no comments; names carry meaning. Comment only when the *why* is non-obvious (invariants, workarounds, surprising GitLab behaviour). The existing comments are all of that kind; keep them.
- Validate at boundaries (user config, API responses); trust internal code.
- Do not write code for hypothetical future requirements.
- New code in `internal/provider/` needs unit tests in the same package, table-driven where it helps.
- Conventional commit titles (`feat:`, `fix:`, `docs:`, `chore:`, `test:`) for anything user-visible.
